# T2: measured guest requirements

T1's operator-controlled root can change the agent, logging or serving code after boot; a valid hardware report does not by itself establish those properties. T2 needs a reproducible, versioned image and a verifier policy binding its full boot chain and runtime configuration to approved measurements.

* **SEV-SNP:** provider must expose genuine SNP reports and the launch digest, a known firmware/boot chain and measured kernel/initrd/command line (e.g. correctly configured kernel-hashes), CPU policy and collateral. The verifier must validate signatures, TCB, debug/migration policy and an approved launch measurement. SNP launch measurement alone does not automatically cover an arbitrary mutable root filesystem. See [Linux SNP launch documentation](https://docs.kernel.org/virt/kvm/x86/amd-memory-encryption.html).
* **TDX alternative:** expose quotes, collateral, MRTD and RTMR event log; replay the log and validate RTMRs and the approved boot chain. Verify report data binds the keys, WG key and workload digest under the v2 contract. A self-reported image digest alone is not a measurement.
* **Runtime:** authenticated dm-verity rootfs with its root hash anchored in the measured boot chain, verified immutable serving/agent artifacts and configuration, secure updates and rollback policy, and no operator SSH or interactive root. Generate TLS/WG/session secrets in guest memory and release sensitive keys only to a fresh approved quote. Prove application and network policy are included in the measured chain; manage mutable state separately.
* **Provider knobs:** ability to launch a customer-supplied or reproducible image and firmware/boot parameters, request SNP/TDX and GPU CC with passthrough, obtain unmodified guest reports and GPU evidence, control metadata/config injection and boot measurement, disable console/root access, obtain TCB/collateral and site provenance, and update/revoke images. Verda's available image list does not establish that these knobs exist; confirm with the provider.

[Phala's dstack audit](https://docs.phala.com/images/audits/dstack-audit.pdf) describes TDX quote verification, RTMR event-log replay and binding a TLS key to a quote. [Chutes sek8s](https://github.com/chutesai/sek8s/blob/main/docs/end-to-end-miner.md) documents a TDX guest with an encrypted root and release of its LUKS key after measurement checks; its debug image permits SSH and is not equivalent to its protected image. Neither description establishes that Verda's supplied image offers the same guarantees.
